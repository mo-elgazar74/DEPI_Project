# Cache frequent queries (Redis)

## Summary
Implementing a Redis cache to store and quickly retrieve the results of frequent user queries, reducing latency on the VectorDatabaseQdrant|vector database and improving overall system response time.

## Key concepts
*   **Redis** is an in-memory data store, meaning it keeps data in your server's RAM for extremely fast read and write access, much faster than querying a disk-based database.
    *   *Example*: Think of Redis as the top drawer of your desk where you keep the tools you use every day, while your main database is the filing cabinet across the room.
*   A **cache key** is a unique identifier for a stored query-result pair, often created by hashing the query text and its parameters to ensure consistency.
    *   *Example*: `python import hashlib; cache_key = hashlib.md5("What is photosynthesis?".encode()).hexdigest()`
*   **Time-to-Live (TTL)** is a setting that automatically deletes cached data after a specified period, ensuring the information doesn't become stale.
    *   *Example*: Setting a TTL of 1 hour on cached answers for a science quiz app, so new information from updated textbooks is reflected within an hour.

## Why it matters
*   **Dramatically lowers response time** for repeated questions, providing a near-instantaneous user experience, which is critical for interactive applications like the [[RagSystemRoadmap/ChatStyleQAInterface.md|chat interface]].
*   **Reduces load on critical components**, protecting your VectorDatabaseQdrant|vector database and [[RagSystemRoadmap/GeneratorGroqOpenaiMistral.md|LLM generator]] from being overwhelmed by identical requests, especially during traffic spikes.
*   **Saves costs** by minimizing the number of expensive operations, such as [[RagSystemRoadmap/EmbedUserQuery.md|embedding generation]] and [[RagSystemRoadmap/QueryQdrantForTopKChunks.md|semantic search]] calls, and reducing LLM inference tokens.

## Core steps
*   **Intercept the query** between receiving the user's question and starting the full RAG pipeline to check if an answer already exists in the cache.
    *   *Reason*: This avoids the computational expense of the entire retrieval and generation process for known queries.
    *   *Example*: `python cached_response = redis_client.get(cache_key)`
*   **Generate a unique cache key** by creating a hash of the normalized user query and any critical parameters (like `grade` or `subject` from [[RagSystemRoadmap/DropdownsForGradeTermSubject.md|the dropdowns]]).
    *   *Reason*: Ensures that the same question from different users or sessions retrieves the same cached answer.
    *   *Example*: `python key_data = f"{query}-{grade}-{subject}"; cache_key = hashlib.sha256(key_data.encode()).hexdigest()`
*   **Store the final answer** in Redis with a sensible TTL after a new answer has been generated by the full [[RagSystemRoadmap/Phase6GenerationLayer.md|generation layer]].
    *   *Reason*: Makes the result available for future requests without recomputation, while the TLL ensures data freshness.
    *   *Example*: `python redis_client.setex(cache_key, ttl=3600, value=json.dumps({"answer": final_answer, "sources": source_list}))`

## Checks
*   Is the cache key consistent for the same query?
    *   ✔ `"what is gravity"-"grade5"-"science"` always produces the same hash.
    *   ✘ `"What is Gravity?"` and `"what is gravity"` produce different keys due to case sensitivity.
*   Is the TTL appropriate for your data's volatility?
    *   ✔ TTL of 24 hours for a stable curriculum knowledge base.
    *   ✘ TTL of 30 days for a knowledge base that is updated weekly.
*   Does a cache hit bypass the vector database and LLM?
    *   ✔ Logs show a direct response from Redis with no calls to [[RagSystemRoadmap/QueryQdrantForTopKChunks.md|Qdrant]] or the [[RagSystemRoadmap/GeneratorGroqOpenaiMistral.md|LLM API]].
    *   ✘ Logs show that [[RagSystemRoadmap/EmbedUserQuery.md|embedding generation]] still occurs on a cache hit.

## Failure modes
*   **Serving stale answers** happens when the TTL is set too high and the underlying source data in the VectorDatabaseQdrant|vector database is updated.
    *   *How to fix*: Implement a cache invalidation strategy that purges relevant keys when new documents are added via [[RagSystemRoadmap/IndexAddNewDocuments.md|document indexing]], or use a shorter, more conservative TTL.
*   **Cache key collisions** occur if the key generation method is flawed, causing different queries to map to the same key and return the wrong answer.
    *   *How to fix*: Include all relevant parameters in the key (e.g., query, subject, grade) and use a robust hashing algorithm like SHA-256.
*   **Memory exhaustion** in Redis can crash the cache if too much data is stored without expiration or if the memory limit is not configured.
    *   *How to fix*: Configure a maxmemory policy in Redis (e.g., `allkeys-lru`) and monitor memory usage through your [[RagSystemRoadmap/AnalyticsDashboard.md|analytics dashboard]].

## Examples
*   **Real-world analogy**: A library's frequently asked questions desk. The first time someone asks "Where are the restrooms?" the librarian looks it up and gives directions. For the next hundred people who ask the same question, the librarian can instantly give the same answer without looking it up again, saving immense time and effort.
*   **Code snippet**: A simple caching function in the request flow.
    ````python
    import redis
    import hashlib
    import json
    
    def get_cached_answer(query, grade, subject):
        # Create a unique key
        key_data = f"{query}-{grade}-{subject}".lower().strip()
        cache_key = hashlib.sha256(key_data.encode()).hexdigest()
        
        # Try to get from cache
        cached = redis_client.get(cache_key)
        if cached:
            return json.loads(cached) # Returns {'answer': ..., 'sources': ...}
        
        # If not in cache, proceed with full RAG pipeline...
        full_result = execute_full_rag_pipeline(query, grade, subject)
        
        # ...and store the result for next time
        redis_client.setex(cache_key, 3600, json.dumps(full_result))
        return full_result
    ````

## Advanced notes
*   Consider a **two-tier caching** strategy where you cache not only the final answer but also the results of the [[RagSystemRoadmap/QueryQdrantForTopKChunks.md|semantic search]] itself, which can be useful if the same context is used for slightly different query phrasings.
*   For even greater performance, explore using Redis modules like **RedisJSON** to natively store and query the structured response data, avoiding serialization/deserialization overhead.
*   Monitor your cache **hit rate** (the percentage of requests served from the cache) via [[RagSystemRoadmap/AnalyticsDashboard.md|analytics]]; a low hit rate indicates your caching strategy may not be effective for your query patterns.
